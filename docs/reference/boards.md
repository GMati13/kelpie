# Boards

The board layer and its three boards (Jira, a GitHub Project, a Linear team), Jira's sign-in and time estimates.

## Board layer

Board layer (`board.js`): every question the story views ask a profile's board goes through it: `loadBoard()` (the stories, subtasks, columns and sprints, as `StoryList.fetch` keeps them), `ticketUrl()`/`boardSite()`, `description()`, `comments()` (newest last, `{total, list: [{id, author, avatar, at, blocks}]}`, the newest `COMMENTS_MAX` (50): Jira `GET …/issue/<KEY>/comment?orderBy=-created`, the key checked first, bodies by `adfBlocks()`; a Project's `issueComments()` in issues.js, the constant `KelpieComments` query (`comments(last: 50)`, with `rateLimit`), bodies by `markdownBlocks()`; a Linear team's `linearComments()`, the constant `KelpieLinearComments` query (`comments(first: 50)`, sorted by when each was written, as Kelpie doesn't rely on Linear's order), the key checked first, Markdown; authors' names cleaned by `commentAuthor()`; both demos from an issue's fixture `comments` `[{author, at, body}]`, `demoCommentsOf()`), `ticketText()` (the review prompt's), `lookUp()` (Claude's picks off the list), `statusOptions()` and `moveStatus()` (the status chip), `doneOption()` (Move to Done).

Which board a profile has is `boardOf()` in config.js (`{kind, cfg, name, prompt, orchestrator, handover}`, from a profile or a setup alike, null without one) and `hasBoard()`: every "does this profile show stories" asks it, never `jira` itself (`board.test.mjs` checks no view calls `jira()` or reads `.jira`; only board.js, config.js, the old Sprint view, the profile dialog and the demo do). A profile's `project` section (a GitHub Project: `boardOf()` kind `project`, name GitHub, with the github section's `account`) is the other board; board.js's header is the shape its load gives. Its address is `parseProject()` (github.com `users|orgs/<login>/projects/<n>` only), its keys `PREFIX-<number>`: a repo's prefix is the profile's (`prefixes`, `"owner/repo=PREFIX, …"`, `parsePrefixes()`, malformed ones throw) else the repo's name in capitals with all but letters and digits dropped (`defaultPrefix()`), and always `PREFIX` (a capital, then 1-19 capitals or digits): what the key finders take (`KEY` in stories.js, sessions.py).

Its load is `loadProject()` (project.js, `loadBoard()` dispatching by kind), through `gh()` as the profile's GitHub account: constant GraphQL queries with stable operation names (`QUERIES`: `KelpieProjectUser`/`KelpieProjectOrg` by `ownerType`, `KelpieStories`, `KelpieSubIssues`, `KelpieKept`), each asking `rateLimit` too (for `ghlimit.js`, under Pull requests), every value (owner, number, cursor, node ids) a `-f`/`-F` variable and never in the query text, the owner and number checked first (`target()`), node ids checked before they're sent, keys checked against `^[A-Z][A-Z0-9]+-\d+$` before they leave. Scope: the first iteration field's current iteration by date (`sprints [{id, name}]`), none running `[]` (no stories), no iteration field the board as a whole (`kanban: true`: open items and those closed in the last 14 days).

Yours: the Project's ISSUE items assigned to you (`assignee:@me is:issue`, a constant filter; drafts, pull requests and archived items skipped), in its position order, up to 10 pages of 100; a story is such an issue's parent, else the issue (one level), fetched by `nodes(ids:)` with only its sub-issues' ids (`subIssues(first: 50) { nodes { id } }`), the sub-issues then asked flat by id (`KelpieSubIssues`), its children: GitHub charges a connection for every item it could hold, nested ones multiplied, so the sub-issues' fields asked inside the stories' query cost 125 points for 61 stories, every load, against 5 asked flat (#129); then the kept stories (`keptProject()`, below under Stories): their issues by the constant `KelpieKept`, `KEPT_SLOTS` (25) keys a query (slots `k<n>` with variables `o<n>`/`r<n>`/`n<n>` and `u<n>` turning the slot on, `@include`, the rest left at their defaults: owner, repo from the key's prefix in this or the last load's `repos`, number; with `viewer { login }`), as one each cost a point a key every load; a slot GitHub answers `NOT_FOUND` comes back null beside the others (`ask(…, {partial: true})`), a sub-issue's parent taken, fetched as the others, its issues assigned to the viewer (`assignees(first: 10)`) counted as yours.

With the board's `unassigned` on, one more question, its own constant `KelpieUnassignedUser`/`KelpieUnassignedOrg` (items `no:assignee is:issue`, 3 pages at most, the same scope, a sub-issue's parent's title, page and state for its heading); the pull requests closing those issues don't join `links`. Each issue is dressed as Jira's: `issuetype` Issue/Sub-issue, its status its item's Status option in this Project (`{id: option id, name: option name}`, category `projectCategory()`: a closed issue or the last option done, the first option or one named as work not started (Backlog, Todo, Ready…: GitHub has no categories) to do, the rest in progress), on the Project with no Status `No status` (its item kept), or off the Project `Open`/`Closed` with no id and `item: null`; the first assignee (`name || login`, `avatarUrl(size: 48)`), its labels (`labels(first: 10)`, name and colour).

An issue whose repo makes no prefix is skipped (with its story's sub-issues); two repos with one prefix fail the load, saying to give one its own. `links` (pull request url → key) come from each issue's `closedByPullRequestsReferences`: `prKey()` in stories.js (build(), lone PRs, Your pull requests, `knownKeys()`, the review ticket) takes a key in the title first, else that link. `issue()` keeps an issue's `url`, `item`, node `id` and `closed` (its state on GitHub, for Close in the Done group); `StoryList.fetch` passes `links`, `repos` and `project` through. `ticketUrl()` for a Project: the issue's loaded `url`, else `https://github.com/<repo>/issues/<n>` from `repos`. `description()`, `ticketText()`, `lookUp()`, `statusOptions()` and `moveStatus()` take the loaded data last (`st.data`, or the shared copy), where a Project's issue is found; Jira ignores it.

A Project's answers are `issues.js`: `issueRef()` (`{owner, repo, number, url, item}`: from the loaded issue's `url` and `item`, else `data.repos[PREFIX]` and the key's number; the key checked against `^[A-Z][A-Z0-9]+-\d+$` first, null otherwise), the description `gh api repos/<o>/<r>/issues/<n> --jq .body` after `ISSUE_URL` (github.com issue pages only, as `pullBody()`'s `PULL_URL`) drawn by `markdownBlocks()`, so passages are found in it too; `ticketText()`/`lookUp()` one constant GraphQL query `KelpieIssue` (owner, repo, number as variables; title, body, parent), a sub-issue's parent its story (its key from `data.repos`, else `prefixFor()`). Status: `statusOptions()` is the loaded columns (one option each, `columns[i].statuses[0]`, `projectCategory()`), but the one it's in; `movable()` is false for an issue whose `item` is null (not on the Project): its chip is only the lozenge, its tip saying why. `moveStatus()` (`setStatus()`) is the constant mutation `KelpieMove` (`updateProjectV2ItemFieldValue`, `singleSelectOptionId`) with `data.project.id`, the item, `data.project.statusField` and the option, run only on the person's own click (the chip's menu, or Move to Done's dialog button): the option must be one of the loaded columns' and all four ids match `^[A-Za-z0-9_=-]{1,100}$`, else nothing runs; `MOVED` shows the new status at once, as Jira's.

A demo board runs nothing: the fixture's issue `description` (Markdown), its parent for lookUp, and a move sets demo.js's `MOVED` through `demoMoveTo(key, column)` (the column's first status). A Linear team (`boardOf()` kind `linear`, name Linear, from a profile's `linear` section `{url, workspace, team, keychain, tokenCommand, prompt, orchestrator, handover, solo, moveToDone}`; `parseLinear()`: `https://linear.app/<workspace>/team/<KEY>/…` only, the team's key a `PREFIX`; `buildProfile()` checks a saved one and refuses it beside another board) is the third board, `linear.js` (#12, a first part: the loader and the board's answers; not yet in the profile dialog, `APPLY_KEYS`/`CONFIRM_KEYS`, the configure-profile skill or the demo, so a profile gets it only by hand for now).

Its sign-in is a Linear personal API key, kept as Jira's token is: the Keychain item's password or the token command's first line, only through `linear.sh`'s pipes into curl's `-K -` config as the `Authorization` header (a quote, backslash or line break refused), the script turning tracing off first as jira.sh does, sent to `https://api.linear.app/graphql` alone (written in the script, never passed in), and only Kelpie's own operations (`query|mutation Kelpie…`, `--data-raw`). Every question is a constant in `QUERIES` (`KelpieLinearTeam`, `KelpieLinearIssues`, `KelpieLinearStories`, `KelpieLinearIssue`, `KelpieLinearMove`), values as variables, the issue filter built in linear.js from checked ids.

Scope: the team's active cycle (`sprints [{id, name}]`), a team running cycles with none active `[]`, one without cycles the board as a whole (`kanban: true`: open work and work completed in the last 14 days). Yours: the team's issues with `assignee: {isMe}`, in Linear's `sortOrder`; a story is such an issue's parent, else the issue, with all its sub-issues (`children(first: 50)`, any team's); kept stories by number in the team (other teams' keys skipped), a sub-issue's story taken, yours by the viewer's id. Keys are Linear's identifiers, checked against `^[A-Z][A-Z0-9]+-\d+$` (others dropped). Columns are the team's states in Linear's board order (backlog, unstarted, started, completed, each by position; triage and canceled aren't columns), each with its `category` (`linearCategory()`: started in progress, completed or canceled done, the rest to do); an issue's status is its state, labels keep Linear's colour without its `#`. `ticketUrl()` the issue's loaded url, else `https://linear.app/<workspace>/issue/<KEY>`; `description()`/`ticketText()`/`lookUp()` ask `KelpieLinearIssue` by key (Markdown through `markdownBlocks()`); `statusOptions()` the loaded columns but its own, each with `toId` its own id (so `doneOption()` and `MOVED` read it as Jira's); `moveStatus()` `issueUpdate` with `stateId`, only a key and a state of the loaded columns, on the person's click.

A refused key, none found or Linear's own message are said in plain words (`linear()`). Tests: `tests/js/linear.test.mjs`, `tests/shell/linear.test.mjs`

## Jira's sprint and sign-in

Sprint: `jira.sh <site> <keychain item> search|get|transition`. Sign-in is the Keychain item (account = Jira email, password = API token); the token goes to curl on stdin. Jira answers a rejected token with 200 and an empty anonymous result, so sign-in is judged by the `X-AAccountId` response header, whose id jira.sh prints as `account` (only `[A-Za-z0-9:_-]`, else empty). Columns come from the board's configuration (status ids), all active sprints show, grouped by story like Jira's swimlanes. An issue the board gives whose key, or its parent's, isn't a ticket key (`^[A-Z][A-Z0-9_]*-\d+$`) is left out of the load (`keyed()` in board.js), as keys go into searches, folder names and `{key}` commands

`security add-generic-password -w`'s own prompt cuts passwords at 128 characters (Atlassian tokens are ~192): store with zsh `read -rs` piped into `security -i`, as the setup dialog's Copy command does

## Time estimates

Time estimates (`estimates.js`, #90): the To do and In progress headings show, before their counts and muted, the work their stories still hold by time estimate (`sprintSums()`, through `groupHeader()`'s `aside`, which goes into one tree only as its `trail` does (#133): the skin's `groupDecor`, which gets it too, when the skin draws its own heading, else the plain one; a clock before the time and a gap before the count, so the two don't read as one number): a story counts its own estimate while it's unfinished (not done, not at or past the handover column), else its unfinished subtasks of yours, else itself (`workLeft()`), each ticket's estimate Jira's remaining `timeestimate` first, else `timeoriginalestimate` (seconds; the search asks for both, `issue()` keeps them, `build()` puts `estimate` and `unfinished` on stories and subs), tickets without one counted apart in the tip; no estimates at all (a board in story points only): nothing.

Shown in hours and minutes, never days (`hoursText()`: "45m", "6h 30m", "38h"). When the sprint has an end (each sprint's `end`, its last day: Jira's `endDate` by `lastDay()` in `boardScope()`, a midnight end the day before; a Project iteration's start plus its duration less a day, `iterationEnd()`; several: the latest), To do is weighed against the working time left (`timeLeft()`: weekdays from today, today included, to that day, × the board's `hoursPerDay`, `hoursPerDay()`) less In progress's sum: "8h of 10h 30m free" ("of 24h left" while In progress has no estimate), amber (`working`) when it's more than fits, its tip saying the whole sum. A GitHub Project has no estimates yet (a number field to read is a later part of #90).

The demo's fixture has `estimate`/`remaining` hours on some tickets and its sprint's `startDate`/`endDate` (relative), the Project demo's iteration made from them
