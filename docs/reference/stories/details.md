# A story's details

A story's header and its actions, assignees, tags, status chips, Move to Done and busy runs, the tab bar, descriptions and comments, pull request lines and subtask rows, and passages.

## Header

Header (`headActions()`): one filled main action (Peek when an agent asks, else the most urgent PR action (more than one pull request ready to merge: Merge all ▾, the Merge menu filled, an agent checking them and planning the merge), else Show agent / Resume / Start work, as `cmd-shift-r`; the same for a ticket without subtasks, via its single sub, which has no row of its own: only its PRs list), Pause (the whole story, while it has a space), then after a thin line icons (Request approval and Merge are no longer here but on the story's Ask line, KELPIE-228, below under Ask Claude; Merge all stays the main action), Clean up (a broom, `cleanButton()`, also on the list's rows, and as Clean up all with a count beside the list's freshness line: one `confirm` listing every finished story with something left, `kelpie.clean-all`, `cleanAll()`; shown only while a finished story leaves something to clean, `cleanable()`: its space, paused sessions, or leftovers when the profile has a clean-up command (`checkLeftovers()`, shared `kelpie.clean.leftovers`: the leftovers check's lines, else a ticket folder named after a key; a check running is shared `kelpie.clean.checking` by profile, `{at, until, again}`, past `until` (finished stories × `LEFTOVERS_EACH` 10 s, plus `BUSY_MARGIN`) no longer counting, so a run lost mid-check can't stop the checks for good, nor its late answer overwrite a newer one; a recheck asked for meanwhile runs once it ends, `again`); it opens the `confirm` dialog saying what goes, whose Clean up runs `kelpie.clean-story-<key>`, `cleanUp()`; afterwards the story's own leftovers are looked at again at once (`recheckLeftovers()`), its entry replaced, or removed when nothing's left, and kept over what a check that began before found (`checked` by story, `putLeftovers()`), then the whole profile's, so the broom goes once nothing's left), Refresh, Open in Jira (Open on GitHub for a Project's ticket and for a review), More ⋯ (`menuButton()` in ui.js with `iconPath`, a Popup so short blocks don't clip it; a press anywhere on an open menu stops there (its list's `on_mouse_down`/`on_click`), as what lies under the popup gets it next: a Merge menu's pick over a story's row in the list also opened that story, hiding the Claude it had shown; it keeps state on its `host` as `menu`, `menuShut`, `armed`, so a view with a method of those names (WorkSide's `menu()`) passes a plain object instead; the tab bar's + uses it too: Start fresh (no space yet; with one, more agents come from the tab bar's +, so no New agent here), Start orchestrator, then the earlier sessions on the key to resume) and the fold.

The key opens Jira too; the fold chevron is the row's last item, so the key sits at INSET. Subtask rows keep per-agent Show/Pause/Resume. Who a ticket is assigned to is an initials `avatar()` (ui.js) beside its status chip, in the header (not for reviews or lone PRs) and on each subtask row, "Assigned to <name>" ("(you)" when yours) or "Unassigned" in its tooltip (`assigned()` in stories.js; `issue()` keeps `assignee.displayName` and the 48px `avatarUrls` link as `avatar`). What kind of work a ticket is shows as tags (`tagRow()`, small tinted words, the rest as "+n" in a tooltip): on a list row at its key line's end, as many as fit the room the line leaves, whole, then "+n" (`fittedTags()`, `fitTags()`: the room and each tag's width measured as drawn, hidden copies for the tags and "+n" (a third wider for a two-digit count), kept raw per copy on `this.tagFit` and divided at render by the zoom then known from a 100-wide probe, so the order Herdr reports sizes in doesn't matter; when not even the first fits whole it's cut with an ellipsis to what's left, if that still reads (`TAG_MIN`), else only "+n"; until measured, the first two shrinking), so a tag never runs past the row; a name past 110px (`TAG_MAX`) ends in an ellipsis everywhere; on the title row in the room left before the assignee, fitted the same way (they give way before the title, never pushing the status off the line), on a subtask row at its title's end (two, under the hover actions). `tagsOf()` picks them in `build()` (`tags` on each story and sub): its type unless it's the level's usual one (`usualType()`: every story a Story says nothing; a Project's Issue/Sub-issue is Kelpie's own, `issuetype.madeUp` from project.js, and never shows), then its labels (Jira's search asks for `labels`; a Project's come with their repo's colours).

A bug reads the same on either board (`BUGGY`: Jira's Bug type and a label like `bug` are one tag, first, in the theme's `blocked` red; the whole name must be the word, or the word after a group like `type: bug` or `kind/bug`, so `not-a-bug` or `bug-bash` are plain labels). Colours: a repo's moved toward the theme's foreground until it reads on the background (`legible()`, contrast 4), Jira's (none given) always the same theme colour for a name (`tagColor()`, FNV-1a, never red). Names and colours are strangers' text: `labelsOf()` (used by `issue()`, so the shared copy holds only that) strips control characters, cuts names at 40, keeps 10 and a colour only as six hex digits. The demo's issues have labels (`labels`, colours in its `project.labels`), and ACME-175 is a Bug.

Not on the Done group's rows. With a picture it's Herdr's `Avatar` (the initials as its fallback): after a fresh load the list downloads each assignee's picture once (`fetchAvatars()`, `avatar.sh`: curl https only, the file kept only when it's a PNG/JPEG/GIF/WebP under 1 MB) into `art/kelpie/avatars/<name of its link>.<type>`, as Herdr draws images only from its own folder; shared `kelpie.avatars` notes each file, or a failure tried again a day later. Only links to Gravatar, GitHub's avatar host (`avatars.githubusercontent.com`, a GitHub Project's assignees) and Atlassian's public avatar host count (`avatarUrl()`, checked again by the script): the Jira site's own need a sign-in, and nothing sends one (those keep the initials).

The demo has none, so it never fetches. Status chips (the header's, each subtask's; `statusChip()`) are menus: a click loads the ticket's workflow transitions (`GET …/issue/<KEY>/transitions`, cached a minute), picking one moves it (`jira.sh … transition <KEY> <id>`, the script's one write, key and id checked) and reloads the stories; the new status shows at once (`MOVED`, `noteMoved()`), and not only on its chip: it's put into the loaded stories, the shared copy and the list's own (`withMoved()`), so the story's group, order, progress and Next follow it; each fresh load keeps it put in until its answer shows it, then forgets it (`settleMoved()`), as Jira's search lags behind a move, for 10 minutes at most (`MOVED_FOR`).

A transition whose workflow asks for fields fails with Jira's message in the note. While a ticket moves its chip is the working mark and a second pick is refused (shared `kelpie.busy`, `move:<KEY>`, below). Move to Done (a double-check icon, `finishButton()`, `check-check`, among the header's icons and on each list row under Built / Waiting on others (its clicks kept off the row, as the broom's), while something of the story is yours to move: `donePlan()` in stories.js; unless the board's `moveToDone` is false, "Move to Done" under the Board page's Your part, `finishes()`, which also stops a dialog opened before) moves a story to the board's done column in one go: the person's own subtasks not done yet, one after another, then the story itself, only once every subtask is done (others' subtasks, unassigned ones too, are never moved: they aren't the person's to close, and while one is open the story stays); a ticket without subtasks is moved itself.

Its confirm dialog (`askMoveToDone()`) lists each ticket with the status it moves from, others' as left alone, and the story's line saying whether it goes or why it stays. Its button asks for the move (Confirm's `doneStory`, `moveStoryToDone()`, through a run request, below under Overlays) and closes at once; the run goes on in place, its icon the working mark ("Moving to Done… 2 of 5") and the header saying it in words. It writes to the board, so no `kelpie.*` command starts it, as any agent can run one. Each move is `doneOption()` in board.js (the option landing in the board's last column, by a Jira transition's target status id (`toId`), not its own id, or a Project's last Status option; else one landing in a done status; none, or an issue off the Project: it says why) then `moveStatus()`; one that fails doesn't stop the rest (the story then stays), and the note (and a warning notification) names each with why, to move by hand.

The new statuses show at once (`MOVED`), then the stories reload once; the story is then finished, so the broom offers itself. Next offers the step too, before its clean-up (KELPIE-88): one item for every story ready for Done ("ACME-129: ready for Done, move it", "3 stories ready for Done: move them", the double-check mark; its group "Ready for Done" in the open queue; `get_next` kind `move-to-done`), the rule being `readyForDone()`: something of it yours to move (`donePlan()`), your part done (`sunk`, nothing of it needing you), none of its pull requests open, no agent of it (or in its space) working or waiting, and either the board worked alone (`worksAlone()`: closing it is the person's) or a pull request of it merged (on a team's board a ticket handed over with nothing merged is the testers' to move; merged ones are loaded for 14 days only, so an older one keeps just its row's button); never a reassigned story, a busy one (its key, or a ticket's chip moving), while a Ready for Done run is on (`done-all:<profile>`) or with `moveToDone` off.

A press opens one dialog (`askFinishAll()`; one story alone asks as its own Move to Done): each story's lines as `askMoveToDone()` has them (`doneLines()`), Clean up afterwards when any will be done; its button (Confirm's `doneStories`, `moveStoriesToDone()`, a run request too) runs each story's `moveStoryToDone()` in turn, under `kelpie.busy` `done-all:<profile>`, and the note sums it up: the tickets moved, the stories that stay, what failed. Runs on a story are one at a time: shared `kelpie.busy` (`takeBusy()`/`endBusy()` in stories.js) marks a story being cleaned up or moved to done by its key, a ticket's own chip move as `move:<KEY>`, Clean up all as `all:<profile>`, Run all as `picks:<profile>`, each `{kind, keys, step, on, at, until}` (`on`: the ticket moving now, cleared once the moves end, so no chip spins through the clean-up after them), `until` being the whole run's limit (keys × `CLEAN_EACH` 25 s, or × `MOVE_FOR` 30 s, plus `BUSY_MARGIN`), so a reload mid-run or a command that never returns can't keep it locked.

A second clean-up or Move to Done of a busy story is refused with a note (a second press once ran the clean-up command twice at once), as is Clean up all while it runs; Next's clean-up item leaves busy stories out. Meanwhile its broom (row, header, Clean up all's count) or Move to Done icon is the working mark (`busyMark()`), its tip what it's doing ("Cleaning up ACME-12: 2 of 3…", "Moving to Done… 2 of 5") and how long once past 5 s, said in words in the header (redrawn each second); the tickets in `keys` have no chip menu (the one moving spins). A clean-up also hides the header's other actions, and `once()` and the story's Terminal (`cleaningNow()`) refuse to start or resume an agent or open a terminal on it; Move to Done locks only its clashes (clean-up, another Move to Done, its tickets' chips).

A clean-up command stopped at its 25 s says which key, that what's left is looked for again, and to try again or clean it by hand. No Stop button yet. While the story will be over for you once moved (done, or with every subtask of yours moved, your part handed over though others' keep it open, `overOnceMoved()`), the dialog also has Clean up afterwards (Confirm's `check`, a switch as the profile dialog's, off unless chosen last time: shared `kelpie.done.clean` by profile): ticked, once everything moved, the clean-up's own checks run (`cleanBlockers()` on the story as it is now: done, or handed over once your subtasks are done, then uncommitted work); any failing (or your part not done, a move having failed) cleans nothing and says why in the note and a warning, else the story's leftovers are looked for (`recheckLeftovers()`, replacing its entry: the leftovers check only looks at finished stories, so a story done a moment ago had none recorded and the clean-up command didn't run) and `cleanUp()` runs, its note after the moves'. "No PR yet" is the one wording.

## Tab bar, descriptions and comments

Tab bar (main.js `toolbar`): every tab is the same boxes, shown, hovered or not (10px padding, a 16px slot, 6px gap, the name up to 180px, 10px padding): the slot holds, for a tab with an agent, always its state (`agentMark()`, the tab's status, unknown while its Claude hasn't reported one), and the program's icon only for a tab with no agent, and turns into the ✕ on hover (⌘W closes the shown tab); skins mustn't change a tab's size, weight or border on `active`, drag a tab onto another to put it before/after it (`tabDrag`, `tab.move`), and every new tab opens last (`newTab()` in config.js: Herdr inserts after the shown tab, so it moves the new one to the end; use it, never `run("tab.new")`); the story's tabs (a Claude agent's tab shows its session's name, the title Claude gives its terminal, via `sessionTitle()` in ui.js, once it has one; the tab's own name is its tip), then a + icon menu (Claude ⌥⌘C, Terminal ⌥⌘T; not a tab, hidden for reviews), Overview (previews only), Changes and Screenshots (counts hidden at 0; in a preview only when they hold something: PRs or files, sessions with images, counted once by the title row).

A folded description never ends on a heading: the next block comes too (cut to a few lines when long). The board's columns (`/board/<id>/configuration`, status ids) are in the shared data (`columns`). Descriptions are selectable (Herdr selects text only in a `TextView`: each line is a `TextView.html`, which ignores inherited colour, so it's set on it, and drops `<br>`; a line with inline code flows word by word with the code in a box of ours, as TextView's own code background is nearly the page's). Descriptions (`adf.js`: Atlassian Document Format to blocks) load on demand, `GET /rest/api/3/issue/<KEY>?fields=description`, cached per key in each view's own context and reloaded after the stories reload once 5 minutes old or after Refresh: the story header and the start panel show the story's, folded to about 12 lines, set as a calm reader (14 on a 24px line, lead 16, a centred column about 64 characters wide with padding around it, the opening paragraph as a larger lead, headings as small accent capitals); clicking a subtask's title shows its own under it.

Its comments (`StoryBody.comments()`, `board.js comments()`) load and reload with it (`shownOnce()`, kept in `THREADS`, the `KEEP.comments` written most recently) and show under it, the story's in the description's column and a subtask's under its opened description: a folded "Comments · n" heading (none while loading or when there are none), opened (per key, `PICKED.talk`) to the newest three (`COMMENTS_SHOWN`), newest last, with "Show all n" above them (`PICKED.allTalk`); each its author's avatar (their picture only when the list already downloaded it for an assignee, else initials), name, how long ago and text drawn by `blocksView()`; older ones than were sent are said to be only on the board.

Not passed to any agent. A passage shown (below, Passages) is looked for in them too. The story's Terminal (the tab bar's + menu, `cmd-alt-t`, `openTerminal()`) opens a new shell tab on every press, as Claude does, named `<KEY> terminal`, then `<KEY> terminal 2`… (the lowest number free, so the tab bar shows Terminal, Terminal 2), in its ticket folder when there is one (agents still start at the root); only the press that makes the story's space goes through `once()`.

## Pull request lines and subtask rows

A pull request's line (`pr()`) is its state's mark and title (a leading ticket key dropped), then its `repo#n`, its state in a few words in its colour (`PR_SHORT`; the full words are the tip) and its age (a merged one's from when it merged, `mergedAt`, as a later comment moves `updatedAt`; the tip in words, "Merged 3d ago", "updated 2h ago"), then the button for what it needs (Merge once approved with checks passed or none, `ready()`), each of those three in a measured column (the button's empty on lines without one), so lines with and without a button line up; the whole line opens it. A ticket with no subtasks lists its own under "Pull requests · n", a story the ones naming its own key under "On the story itself", open ones first, newest first (`prOrder()`).

Subtasks come in two groups, yours first ("Assigned to you"), then "Everyone else", each in the list's order; with only one group there are no headings (`subGroups()`). Subtask rows are a calm list: at rest a row shows what you read (the assignee first, as who has it is what's looked for first, then key, title, its agent's mark in a 16px slot, `agentSlot()`, the status chip; descriptions and pull requests under a row start at its title, `SUB_INDENT`); its actions show on the row hovered (`on_hover`, `this.hoverSub` per copy, a row leaving clears it only if it was its own), laid over the end of its title on a solid copy of the row's colour with a short fade (`solidOver()`), so they keep no room at rest and the title has the row; a row stays awake while its ▾ menu is open or its Pause is armed (`subAwake()`), and Peek shows at rest while its agent asks something (`agentButtons(…, {calm})`).

The row is CONTROL high either way. With an earlier session the actions are Resume held to its ▾ as one split button: Start fresh (New agent once the story has a space) and every session on the key with its age. The status chip's column is as wide as its widest chip in the list, measured as drawn (`column()`, `on_size_change` per cell, divided by the zoom from `colProbe()`), so chips line up. No "No PR yet" on the rows: a subtask's pull requests are the lines under it. A waiting agent's Peek takes Pause's place. Rows are at most `ROWS` (760) wide, centred: wider rows read and aim badly on a wide screen. Resume ▾ and the header's More list every session on the key (first keys or title), newest first.

Resume drops a paused entry only once its tab opened, and the header's Resume resumes every paused key one after another into one space: `space.new` returns nothing, so a launch polls `spaces()` up to 3 s for the key-named space before the next agent opens in it, and stops with a note if it never shows. Start/Resume buttons launch once per story key for a few seconds (`once()`, shared `kelpie.launching`, so the header, details and keys copies can't each start one).

## Passages

Passages: `herdr-app do kelpie.show-passage` shows a story of the shown profile with a passage of its description or of one of its comments found and marked, for an agent asked where a ticket says something (`showPassageRequest()` in stories.js: reads `<home>/kelpie/passage.json`, `{key, quote, note}`, writes `passage.result.json` and removes the request, the result saying where the passage is (`passageWhere()`: `{found: description|comment|none, exact, author, written}`, not `at`, which every result gets as its answer time, from the description and comments the views keep, `DESCRIPTIONS`/`THREADS`, loading what's missing into them; a board too slow for `PASSAGE_WAIT` (3.5 s, waited on `sleep`, as mods have no `setTimeout`) leaves `found` out); it only moves what's shown, so nothing waits for a yes, but the key is checked against the key pattern and the text cleaned of control characters and cut). `showPassage()` sets shared `kelpie.passage` (`{profile, key, quote, note, at}`, an hour at most), unfolds the details and selects the story; while it's set, StoryBody's details are the reader (`reader()`): a bar (found, closest match, or not found, Back to the story clearing it, the note wrapping in full under them, the quote their tip), as wide as the reading column and centred on it, its text on the rows', over the whole description, then its comments (a "Comments · n" line, each comment's author line and its blocks, indented as in the Overview), as one `v_virtual_list` scrolled so the passage is centred (`readerScroll`).

Where it is: `findInTicket()` in adf.js, word for word before a closest match wherever it is, the description first, then the comments newest first, closest matches by the share of the quote's words they hold (`findPassage()`'s `share`); the bar says "Here in Priya Nair's comment, 2d ago", or that it looked in the description and its comments. A list entry is an item of its own, so the passage's entry is what's scrolled to. Rows are placed by heights given, so each is first drawn in an invisible copy and measured (`readerH`, as drawn, divided by the zoom from a 100-wide probe); Herdr reports a size only when it changes, so each passage's copy has ids of its own. GPUI's measured `list()` didn't move with `scroll_to_item` (tried). `findPassage()` in adf.js finds the quote in the description's blocks (a Jira ticket's from ADF, a GitHub Project issue's from Markdown) (case, spaces, double and curly quotes, dashes, Markdown marks and `…` for left-out words forgiven), marks its runs (`mark`, drawn as one run by `inline()`) and flags the top-level blocks it touches (`hl`); not word for word, the block holding most of its words (`exact: false`); none, null
