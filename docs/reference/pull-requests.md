# Pull requests and reviews

Every gh call and GitHub's budget, reviews and Start review, Approve, PR buttons, the quick read after a turn, and PR notifications.

## gh, accounts and GitHub's budget

Pull requests: every `gh` call Kelpie makes (searches, PR files and blobs, descriptions, Approve) goes through `gh(account, args)` in pulls.js, which runs `gh.sh <account> …` through `guarded()` (`ghlimit.js`, #129: GitHub's budget is per account, 5000 GraphQL points an hour, shared by every program signed in as it, and Kelpie once used it all, so nothing loaded and the person's own `gh` failed too): a call GitHub refuses for its limits (gh's message, or a GraphQL answer's `RATE_LIMITED` error; a REST answer's output is never read for it, as it may be a description saying anything) stops every call of that kind (GraphQL, or REST `core`) as that account for as long as GitHub's `Retry-After` says (an hour at most; gh.sh asks every `api` call for its response's headers with `--include`, except one passing `-i` or `--paginate`, and `guarded()` takes them off again, reading only the block at the very start, as the body is anyone's text: `splitHeaders()`), else until the budget's reset (`gh api rate_limit`, free, when it says 0 left), else for a secondary limit 5 minutes doubling in a row up to an hour; shared `kelpie.github.limit` (`{[account]: {graphql|core: {until, hits}}}`) keeps it over a reload, and meanwhile `gh()` answers as a failed run saying "GitHub's limit for this account is used up: Kelpie tries again at 4:25 PM" (`limitMessage()`, never GitHub's own words, which name the account's user id).

Each GraphQL answer's `rateLimit` (asked in the loads' and searches' queries) is kept in memory (`LEFT`, one context for every copy), the lowest seen until its reset, as answers within one load were seen to alternate between two counts (#149); under a tenth left (`lowFor()`), a GitHub Project's story list loads at most every `LOW_EVERY` (10 minutes) whoever asks, and the quick pull request reads' 20 s timer stops until the reset (a turn ending still reads, #146); a card under the freshness line says either in plain words, whole (`limitCard()` in stories.js: used up, the stories are as they were at their load's time and can't update until the reset; running low, they update every 10 minutes until then and may be a little behind; the freshness line then doesn't repeat it, as a note there was cut off before its time).

A refused load keeps the last stories and shows their own age, not the failed load's (the list takes the shared copy before its first load too), and a Jira board's load keeps the last pull requests and reviews rather than none. Then: with the profile's `github.account` (the profile dialog's GitHub page, "GitHub account": Default or one of the accounts `gh auth status` lists, `githubAccounts()`) it asks `gh auth token --user <account>` and hands that token to the one gh run as `GH_TOKEN`, never in arguments or a file (gh.sh checks the login with a `case` pattern, never grep, which checks each line alone, passes the token to no command, and turns tracing off first, as jira.sh and `bin/gh` do: macOS's sh takes xtrace from an exported `SHELLOPTS`, which printed the token); Default runs plain gh on its active account. gh keeps one active token per host in the Keychain, shared by every `GH_CONFIG_DIR`, so another account signing in anywhere on the machine silently swaps it (a profile's own pull requests then vanish, as the search answers as someone else): naming the account avoids that.

Agents and terminals get it as `KELPIE_GH_ACCOUNT` (Claude accounts, below). `gh api graphql` search with `user:<owner>` (covers organisations), review requested and yours, with checks and review state. GitHub gives `reviewDecision` only where the branch requires reviews (null elsewhere, approved or not), so `searchPulls()` in pulls.js fills it from `latestOpinionatedReviews` (a change request wins, else an approval). In the marks changes requested outrank failing checks, failing checks an approval, and an approval the rest (`prState()` in ui.js), and the buttons follow the same order (`askFor()` in stories.js: Address comments before Fix checks, as the header's main action is `need()`'s kind and a pull request in both states once had none); review rows carry a small approved mark (`plain()`'s badge).

What a load may ask of GitHub is held by `tests/js/budget.test.mjs` (#150): a realistic Project profile's full load (60 stories, 40 sub-issues, 120 items, 25 kept stories, 23 pull requests) against a fake gh, at most 12 requests, 4 at once, 25 points by GitHub's own prices (dryRun, written in the test: measure again when a query changes), and 1,000 points an hour with the timer's loads and the quick read's; today 10, 4, 21 and about 810

## Reviews

Review agents open in the profile's `Reviews` space, a tab `PR <repo>#<n>` each. Every ticket's heading under Reviews for you ends in Review (an `eye` icon menu, `reviewTaskRows()`), whether the ticket is a story of the list or not (most reviews are of others' stories, which aren't; one not in the list is its key alone, its title from the board when it can be read, else the prompt names it by its key, `storyReviewTask()`): one agent reviewing all of that ticket's pull requests waiting for you together, against its ticket (`startStoryReview()`: each checked out one after another as Start review does, a tab `Review <KEY>`, shown again when open, started in the profile's folder by `openInReviews()`; its first message `storyReviewText()`: the profile's `github.storyReviewPrompt`, `{prs}` each pull request's rebuilt link and checkout, and the story's key and page), or that review sent to an agent already reviewing them (`sendStoryReview()`, not while it waits for you); with one pull request it's that one's own review, a plain icon.

A pull request naming no ticket ("No ticket") has its own Review icon on its row (`reviewIcon()`), Start review without opening it; the rows under a ticket's heading have none. These icons, and the "No ticket" heading's menus, are the size of a story row's actions (`ROW_CONTROL`) in their column, the row's at their height (`ACTIONS_TOP`), so every icon down the list lines up. A `Review <KEY>` tab isn't the story's own agent (`tabKey()`, used wherever a tab name gives an agent's key). A pull request's header, ⌘⇧R and its row's icon show the agent reviewing it, its own or its story's (`reviewAgentTab()`, `showOrStartReview()`), and its Post comments, Approve with comments and Request changes go to that agent, each naming the pull request (`{prs}` in their messages); Approve stays the person's own click.

Start review (`startReview()`) first checks the PR out (`REVIEW_CHECKOUT`: a detached worktree `<profile folder>/worktrees/review-<repo>-<n>` from the clone at the folder's top or one level down, fetched from `origin pull/<n>/head`; started again it moves to the latest commit unless it has tracked changes, when it's left as it is and the agent reads the pull request from GitHub, as the prompt says the folder holds its latest commit; no clone or a failed fetch: the agent starts at the profile's folder and the note says why, git's message on one line as only the script's last line is read) and finds the ticket its title names (its key and page, `ticketLink()`: the agent reads the ticket itself, KELPIE-302), then starts the agent in the profile's folder, never inside the checkout (it's someone else's code: Claude would take in its settings, hooks and CLAUDE.md there), with the profile's review prompt, which names the checkout as code to read: placeholders `REVIEW_FIELDS`, and a line whose placeholders all came out empty is dropped.

The default reviews by reading only (nothing run, built, installed or tested) and has the agent read the pull request's description and its ticket itself.

## Approve

A review's header always offers Approve, the person's own: a second click approves it on GitHub as them (`approvePull()` in pulls.js: only a `https://github.com/<owner>/<repo>/pull/<n>` address, the reviews API with no shell, pinned to the list's `headRefOid` when it's a full sha; the demo keeps it in memory), never through an agent and no command an agent could run. While GitHub answers, it's Approving… with a spinner (`doneButton()`, the `working` mark; `this.approving`, by url). Once you approved, it's Approved in its place (`doneButton()` in ui.js: the same size, the approved mark, tinted `done`, nothing to click), from shared `kelpie.approved` (url → when, a day) until the stories load again after it, then from GitHub's `viewerLatestReview` (`viewerReview` on each pull request, kept with `headRefOid` in the shared copy by `pull()`), so a later change request shows too.

While its agent runs, it also offers Post comments, Approve with comments and Request changes (`/kelpie:post-review`, `/kelpie:approve`, `/kelpie:request-changes`, or the person's own `post`, `approve` and `changes` messages), each a second click and sent to that agent (`hc send`, not while it's blocked); the review skill has the agent draft only, so nothing is posted until one is pressed. PR and session titles only count keys of the board's projects (from the loaded issues; a leading `[KEY]` always counts), so `UTF-8` isn't a ticket; the story space's last tab closing ends the space and the story's row loses its space mark and Resume is offered. A key with no open or paused agent offers its latest session: `sessions.py` records the keys of the first message of each session (`first`) and of all yours (`keys`).

## PR buttons and the quick read

PR buttons: Fix checks, Address comments, Merge (a confirming second click), each sent to the PR's agent (`hc send`, not when it's blocked waiting for you), else as the first message of a resumed or new one (a new one gets the ticket prompt first); while a launch on the story is still starting (`launchHeld()`, what `once()` would hold) it says so instead of "Asked". An agent finishing a turn (working to done/idle) reads the profile's open pull requests and reviews again at once (`quickPulls()`: `readPulls()` in pulls.js, one constant GraphQL query `KelpiePulls` by their node ids, kept as `id` from the searches, each id checked against `^[A-Za-z0-9_=-]{1,100}$`, with `state`; with the profile's GitHub owner the same question also asks for your 10 newest open pull requests, GitHub's own list of them (`viewer.pullRequests`, `KelpiePullsNew`, or `KelpieNewPulls` alone while none is loaded), not the search, keeping only those under the owner's address: one an agent just opened, which the search's index finds only later, joins Your pull requests or its story at once, marked `opened` in `FRESH`), and does so every 20 s (`QUICK_EVERY`) while something is in flight (`inFlight()`: checks running on one of yours, or an agent of the profile working, as it may merge or push mid-turn): what they say now goes into the loaded stories at once (`FRESH`, `patchLoaded()`, the shared copy and the list's own, written only when it changes something, as every copy draws again on a write), and a load that began before that read doesn't put the older state back (`settlePulls()`; a merge read here stays until a load shows it, as the search lags behind a merge, and so does one newly opened; one closed unmerged leaves the lists; 10 minutes at most); asked for while one runs, it reads again once that ends.

A turn ending starts no full load (#146: one after every turn, at most every 30 s, was most of what an account spent while agents worked, up to ~2,100 GraphQL points an hour): the board and the searches wait for the 2-minute timer or Refresh. While GitHub's budget runs low (`lowFor()`) only the 20 s timer's reads stop; a turn ending still reads (`quickPulls(cx, {direct: true})`), as reacting to what just happened is what the read is for; used up, nothing asks; an agent tab opening or closing reloads only the sessions (`loadSessions()`; asked for while a full load or another sessions read runs, it reads them once that ends, `sessionsAgain`, as that one read them when it began). No Release button: deliberately dropped, don't bring it back

## PR notifications

PR notifications (`notifyPulls()` in stories.js, after a fresh load by the list, not a sessions-only reload): a PR newly failing checks, getting changes requested or ready to merge posts `notify()`; its click selects the story's space, or for a story not started runs `kelpie.show-notified-<id>` (mod commands take no arguments: shared `kelpie.notify.show` maps each id to its profile and key, for a day; bare `show-notified` shows the latest). Last seen state per PR url in `kelpie.notify.prs` (by profile); the first load after a start only records; skipped while PRs failed to load. Profile toggle `notify.pulls` ("Notify about pull requests", default on; `notify.waiting`, agents waiting on you, is under Agents waiting in silence).

Herdr notifies blocked/done agents itself
