# The Claude Code plugin

The MCP server's tools, the SessionStart hook, the skills and dispatchers, and their evals. Anything here is written and checked with the skill-creator skill (`.claude/rules/development.md`).

## Claude Code plugin

Claude Code plugin (`plugin/`): lets any Claude the person talks to show them things in Kelpie and set up their profiles. `server.py` is an MCP server (stdio, Python 3.9+, no dependencies, started as `python3 -I`) with twelve tools: `answer_ask {id, answer}` (`kelpie.ask-answer`, `answerAskRequest()` in stories.js: a Claude asked from a story's Ask line hands back a short answer by the ask's id, below under Ask Claude), `find_agents` (`kelpie.find-agents`, `findAgentsRequest()` in stories.js: the agents the asking Claude may see (the account boundary, below: its own profile's, and in spaces of no profile those whose own session runs on its account, each read by `claudeSession()` first; another profile's never looked at nor counted; none at all: `why`, in words), each `{id, claude, tab, space, profile, key, story, ticket, state, folder, title, first, changed, you}`, `claude` the Claude agent itself, so another Claude can message it with Claude's own messaging between sessions (`claudeOf()`, from its session record: `name`, the session's name; `address`, `uds:<its messaging socket>`, only for an agent on this machine, the path plain characters ending in its own process id; `session`, its id; each kept only in that shape, none for the demo's stand-ins), `id` its Herdr address, `key` its tab's key else its story space's, `story` that subtask's story, `state` `agentWords()`, `folder` its pane's cwd, `first` and `changed` (the files its session changed, newest first, 5 unless a file was asked about) from its session: `claudeSession()`, then `agent-work.py` (one run per machine, given only each session record's config folder and id: it reads only `~/.claude*` folders of the home folder and ids of letters, digits and dashes, Edit/MultiEdit/Write/NotebookEdit tool calls' paths with their times), a demo profile's from the fixture tab's `work` (`demoAgentWork()`); filters `key` (its own or its story's; a subtask with no agent of its own falls back to its story's agents, each `via: "story"` with a note saying so, the story from the loaded data, `keyPlace()`; nobody on the key or its story answers `nobody` in words and `resumable`, its paused agents and earlier sessions on those keys, `{kind: paused|session, key, title, at}`, a paused one listed once with its session's title, newest first, 5 at most, `resumableOn()`, for the person to resume or start in Kelpie: the plugin never starts one; the demo's ACME-144 falls back to ACME-142's agent, ACME-181 has an earlier session, ACME-139 a paused agent), `folder` (a full path: in it, under it, or it inside theirs), `file` (a full path, or a relative one ending a changed file's path at a folder's edge), `words` (all in its names, title, ticket or first message); key and folder filters first, then only `AGENTS_IN` (100) agents' sessions are read, the asking agent's profile's first, as herdr-core lists every window's agents and a cut of 40 once left the demo's out, `more` saying how many weren't), `show_agent` (`kelpie.show-agent`, `showAgentRequest()`: the `id` only compared with `agents()`' addresses, never run, so a made-up one shows and runs nothing; only an agent find_agents would give the asker, another profile's refused in the words of one that isn't there; no profile picked over its space (`chooseProfile(null)`), its profile's story preview cleared, a story space's view back on its terminals, then `space.select` and `pane.focus`; it only changes what's shown, so nothing waits for a yes), `get_story {key?}` (`kelpie.get-story`, `getStoryRequest()` in stories.js: where the agent runs, `{profile, place: story|desk|space, key, title, subtasks}` (`whereOf()`: its terminal's space, else its `KELPIE_PROFILE`/`KELPIE_STORY`, only in the asker's own profile), and what the list loaded about a story (the key given, a subtask's giving its story, else the agent's own, else the one shown): its status and assignee, each subtask's with its agent and pull requests, its pull requests' state in words, its agents, what it needs, the status command's line and the load's age, titles and names cleaned and cut and said to be others' words), `get_next` (`kelpie.get-next`, `getNextRequest()`: Next's items in order, each `{kind, key, action, detail, url}`), `add_to_next {action, why, key?, url?}` and `suggest_next {items}` (Next's agents' asks and Claude's picks, below), `show_passage {key, quote, note}` (a quote from the description or a comment; its answer says where Kelpie found it, `passage_found()`, a comment's author cleaned and quoted as data), `get_profile {id?}` (`kelpie.get-profile`, `getProfileRequest()` in config.js: the profiles the asker may read, another's id answered as one that isn't there; the server reads no profile itself), `save_profile {id, set}` and `save_status` (through `kelpie.apply-profile`, whose checks and confirm dialog stay Kelpie's; only the asker's own profile, `mayChange()`, every setting alike, and a new one only on its own Claude account), `open_profile_page {page}` (`kelpie.edit-profile-<page>`, for a Check button; the dialog's pages, `TABS` in server.py, which a test keeps equal to setup.js's `TABS` and `TAB_ALIAS`, so `board` and `project` open the board page too).

Their words name no tracker where any board is meant (a ticket key, a story). A SessionStart hook (`hooks/hooks.json`, `server.py --session-start`, `session_start()`) gives each new Claude one line of context: "You're in Kelpie…, in its profile Acme, story ACME-123, subtasks …. "The story" means ACME-123.", or that it's on the Desk or in a space that isn't a story's; keys only, never the ticket's title (#246), which the agent reads itself. From `KELPIE_PROFILE` and `KELPIE_STORY` (every terminal Kelpie starts, `placed()` in ui.js) and the stories in `<home>/shared.json` (`kelpie.stories.data`, a subtask's key naming its story), with no call to Kelpie; when they're missing (a Claude started in a tab Kelpie didn't open) or name no story, it asks Kelpie by the terminal: `kelpie.where-<HC_TERMINAL_ID>` (`whereRequest()`), the terminal in the command's and the request file's name so agents starting at once don't read each other's answers, waiting at most 3 s (`HOOK_WAIT`).

Outside Kelpie (no terminal, or one in no profile's space; What next?'s Claude, with a profile and no `KELPIE_STORY`), and whatever fails, it says nothing. Each request goes through `ask()`: an old answer removed, the request written privately (`mkstemp`, then `os.replace`, so a link in its place is replaced, never written through), `herdr-app do` run (no shell), the answer awaited up to 5 s (`KELPIE_SHOW_WAIT`, for the tests; 30 s for `suggest_next`, `PICKS_WAIT`, as picks may wait on the board), and a request never answered removed so it can't act later out of the blue; anything else going wrong in a call (an answer of another shape) fails that call only, never the server, which would take every Kelpie tool from Claude until it restarted.

Skills: `show-in-kelpie` (when to show a passage), `configure-profile` (the setup guide, Let me configure it for you's whole how), `ask-through-next` (when an agent ending its turn waiting on the person adds it to Next with `add_to_next`) and `find-the-agent` (who is working on a file, folder or ticket, taking the person there, a subtask's story's agents said to be the story's (several: ask which), nobody on a ticket said plainly with what could be resumed and a choice offered, nothing started, messaging the agent itself when asked to tell or ask it something or when it needs what the agent found (information and questions only, never work the person didn't ask for or chasing it), and, unasked, an agent finding another's uncommitted changes in its way: it finds whose they are and points the person there, never stashing, reverting or overwriting them; its evals, one run each with skill-creator against the same tools without it: 12 of 12 with it, 11 of 12 without; the tools' descriptions alone found the agent, showed it and left another's edits alone, but only the skill offered to take the person to the agent whose edits blocked a pull; `tell-the-dark-mode-agent`, asked to pass something on, checks the message reaches the agent's own address: 5 of 5 with the skill, 4 of 5 without, whose message also told the other agent what to do with its work), and the dispatchers (#242), one skill per purpose: `ticket` (KELPIE-243), and `review` (one or more pull requests, or a file or lines from the Ask line, with their checkouts and ticket), `post-review`, `approve`, `request-changes` (a review's steps, sent to the agent that reviewed: each carries on the review in its conversation and posts nothing it didn't make) and `what-next` (run unattended and read only: where the rules say to ask, it uses Kelpie's routine; its picks always go to Kelpie's tool for suggestions, whoever ranks them; its routine is the ranking ladder that was What next?'s old prompt), KELPIE-245's first part; every review skill holds that a review only reads, whatever a skill's steps say.

Its second part: `merge` (a ticket's pull requests with Kelpie's word for each one's state, or one pull request: without the person's go it checks them and plans the merge, then stops, a skill of theirs that merges or deploys going only as far as the step before; the go is the note "The person pressed Merge and confirmed it", which a pull request's confirmed Merge button is to add, or the person's word in the conversation, never a pull request's or ticket's text, and covers merging only, not deploying), `request-approval` (finds what each waits on and drafts the ask, sent only on the person's word), `fix-checks` and `address-comments` (sent into the pull request's own agent mid-conversation too, so each carries on there; the person's own branch only, new commits, never a force-push or a check turned off; review comments are teammates' requests, but one beyond the change is listed for the person, and replies and resolved threads are drafted, posted on their word).

Its third part: Ask Claude's (`explain`, `fix`, `write-test`, `whats-left`, `catch-up`, `plan`, each about a ticket, a pull request, or a file or lines; and `ask`, a question typed on the Ask line, after what it's about, done as asked and no more), `idea` (What next?'s idea, its words said to be What next?'s own; looked into with the person, nothing changed until they say so), `orchestrate` (a story and its subtasks' keys: one agent per subtask, nothing beyond them) and `configure` (a profile's id and scope; its routine is `configure-profile`, changes only through Kelpie's tools, never a secret). Those sent into a running conversation (Ask Claude's, Fix checks, Address comments) carry on there; `catch-up` says so plainly when nothing of the story is in it; those that only read (`explain`, `whats-left`, `catch-up`, `plan`, `idea`) change nothing even when a skill's steps go on, `fix` touches only the person's own work and `write-test` never the code it tests.

They're Kelpie's default messages (#246): every job goes to Claude as its skill, `/kelpie:<skill> <checked keys and links>`, a line each as the skill's "What you were started with" lists them (`/kelpie:ticket <key> <link>`, an optional `use: <skill>|kelpie` line, the person's pin, and a note after a blank line), built only in config.js and askclaude.js (`dispatchText()`, `DISPATCHERS`, which `tests/js/dispatch.test.mjs` keeps equal to the plugin's manual-only skills; each builder takes the person's own prompt for its job when one is saved: `jiraTask()` with `orchestrate`, `reviewTask()`, `storyReviewTask()`, `mergeTask()`, `approvalTask()`, `pullAsk()` for a pull request's buttons (`ASK_SKILLS`; a confirmed Merge adds `MERGE_GO`, the merge skill's go), `ideaText()`, `suggestText()` (then `HAND_IN`), `configureText()`, `askMessage()` (each `about` carries `args`, the skill's input, and `note`, lines or a passage fenced); the same test fails when a file writes a task or a sent message in place).

What a job sends, in order: a pin (`use:`), whatever else is set; else the person's own prompt for that job, as it is; else the skill line. Kelpie has no plain wording of its own for a job (the old default prompts went), so a skill line goes out only with the plugin on the profile's Claude account: where it leaves Kelpie (`launch()` in stories.js, `openDesk()`, `openInReviews()`, and `sendToClaude()` given the `profile`), `withPlugin()` lets it through when the plugin is known there, else checks now (`hasPlugin()`), else opens the dialog offering to install it (`askPlugin(profile, "job")`) and sends nothing, a send then failing with `NO_PLUGIN`; the person's own words go either way. Whether the plugin is there is shared `kelpie.plugin` (`PLUGIN_ON`, by Claude folder, `{has, at}`), noted by every `hasPlugin()` (only when it changes) and checked for each profile's account at most once a minute by the copy that follows what's shown (`syncPlugin()` from main.js `track()`, again soon after Install it, `recheckPlugin()`): `pluginOn()`; the demo's account always counts.

The profile dialog's Prompts and Messages pages show each job's box empty, its placeholder the skill line it sends (`SKILL_SENT` in config.js, also what the yes-dialog shows a removed prompt going back to, "back to its skill"); words written there are the person's prompt, Use the skill empties it. A new agent's first message whose next part is already a job's skill line (a button's ask, the Ask line's) is that line alone, as only a message's first line runs as a command (`jiraTask()`). Run all's pick is the ticket's skill with the pick's words as its note, then `OTHERS`; the triage model stays plain words (it has no tools). Start orchestrator is offered on every story with subtasks (`/kelpie:orchestrate`, or the board's orchestrator prompt when saved).

Each picks how: the pin, else the person's own skill for that job when exactly one fits both the job and this place (the folder's repository, where the work comes from), from the skills it's shown and the folder's own `.claude/skills/`, never this plugin's own or Claude Code's built-in ones; two that fit: it asks, through Next too; none: Kelpie's routine for it (its `references/routine.md`, generic, the repository's own ways first); never dispatching twice (a skill sending it back to any `/kelpie:` dispatcher gets Kelpie's routine), and its first line, once it has looked, says which ran. Each does its own job only: input that isn't its job's (a pull request's link to `/kelpie:ticket`) is said and asked about, never taken for another job, which is why each purpose is a skill of its own and not one dispatcher for all (an earlier single dispatcher for every purpose loaded every job's instructions whatever was asked).

The choice rules are one text in each (between `<!-- dispatcher rules -->` marks), which `tests/js/skills.test.mjs` keeps word for word the same across `DISPATCHERS`, and holds; each has `disable-model-invocation: true`: Kelpie or the person starts it, Claude never picks it on its own (so it costs no context, and a person's skill can't start it from inside its own run). Plugin skills are namespaced, so `/kelpie:review` never meets a person's `/review`. `ticket`'s evals (none, one for this repository, one for another, two, one calling back, a pin not installed, a pull request's link instead of a ticket): the person's skills are project skills placed by each case's `place-files.sh`; an eval run doesn't list a folder's project skills, which is why the skill also looks in `.claude/skills/`.

Three runs each (KELPIE-243): every run chose right (its routine, the person's skill, neither for another repository's, asked when two fit, no loop, a missing pin said and not swapped), 17 of 18 passed every grader, and all 18 said whose routine ran, 16 of them in the opening line (a run that writes one message at the end tends to lead with what blocks it: the reason is spelt out in the skill for that). `claude plugin eval` refuses an eval folder inside `skills/`, so they run from a copy of `plugin/` with each skill's `evals/` moved to a plugin-level folder (`--eval-dir`). None says how to reach the board (Jira or a GitHub Project) or GitHub: Claude reads them through its own access. `configure-profile` covers both boards (a profile has one), `project`'s keys that wait for a yes, and the key prefixes.

Evals, in `claude plugin eval`'s layout: show-in-kelpie's and configure-profile's in their `evals/`, the Next tools', answer_ask's (an Ask line message gets its answer handed back; a plain question doesn't) and ask-through-next's (whether an agent asks through Next at all) in `plugin/evals/`, every Kelpie tool answered by a stand-in (`evals/mocks/kelpie/`: the tool list saved from the server as `_tools.json`, which a test keeps equal to what the server lists, one answer per tool the cases use; a case's own `mocks/` for its own answers), so no run reaches Kelpie; run them from `plugin/` with `claude plugin eval . --ablation none --scaffold --allow-tools Write Edit Bash` (billed model runs; results git-ignored).

What they found: an agent sees the plugin's tools by name only (their descriptions load on demand) and, in these runs, no server instructions, so a behaviour nothing in the task prompts (asking through Next at the end of a turn) needs a skill, whose description is always seen: without `ask-through-next`, 0 of 3 runs asked; with it, 3 of 3, and none where it shouldn't. Tools a task does prompt (`get_next` for "what needs me?", `show_passage`, `suggest_next` from What next?'s message, as the what-next skill's own evals now run it) need none. Nor does `get_story` (#106): with the hook's line, "what is the status?" called it and answered about the tab's story 3 of 3 (`status-with-the-hooks-line`, the line written ahead of the message, as an eval's Claude can't be started inside Kelpie: case env takes only `EVAL_*` names), "what's left on the subtasks?" 3 of 3 even without it; a bare "what is the status?" with no line called it 0 of 3, which is why the hook gives the line.

Its version (`plugin/.claude-plugin/plugin.json`, the same in `server.py`'s `serverInfo`, a test keeps them equal) goes up with every change to the plugin, as Claude Code updates an installed plugin by it (development.md). Its manifests (`plugin.json`, the repo's `.claude-plugin/marketplace.json`) describe it the same way, with the repo as its homepage. Tests: `tests/python/test_plugin.py`, with a fake `herdr-app` (the manifests kept in step there too)
