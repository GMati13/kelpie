# Accounts and sessions

Claude accounts per profile, the GitHub account and Kelpie's own gh, the footer's limits, the account boundary between profiles, and the session index.

## Claude accounts

Claude accounts: a profile's `claude.config` (profile dialog, "Claude account": Default or one of the other `~/.claude*` folders found, `claudeFolders()`: those with a `settings.json` or `projects/`; the dialog's hint and the README say so) is the config folder its Claude runs on; Default means nothing set, Claude's own `~/.claude` (no Herdr-level default). `herdr-app do kelpie.claude-<profile>--<folder>` asks to set it from outside (`.claude` clears it), confirmed in a dialog like an agent's change. `claudeArgv(profile, ...args)` in config.js builds every new agent's argv: `env CLAUDE_CONFIG_DIR=<dir> claude`, plain `claude` for Default, and `env -u CLAUDE_CONFIG_DIR claude` when the folder chosen is `~/.claude` itself (set to it, Claude would look for its `.claude.json` inside it).

Resumes keep the session's own folder (`resumeArgv`). Plain terminals the Kelpie layout opens (+ Terminal, a story's Terminal) start as `env <that account> CLAUDE_ACCOUNT_CHOSEN=1 $SHELL -l` (`shellArgv()` in config.js; the account goes to its `sh -c` as an argument, never into the script), so a typed `claude` there uses the profile's account whatever the folder (a shell function that picks an account by folder can leave it alone when `CLAUDE_ACCOUNT_CHOSEN` is set). The profile's GitHub account goes the same way: new agents (`claudeArgv()`), resumes (`resumeArgv(id, config, account)`) and these terminals start with `KELPIE_GH_ACCOUNT=<login>` and `KELPIE_GH_BIN=<the mod>/bin` (`githubEnv()` in ui.js, a login only, never a token; in `shellArgv()` arguments too).

Every agent and terminal Kelpie starts is also told where it runs (#106): `KELPIE_PROFILE=<id>` and `KELPIE_STORY=<key>` (empty on the Desk, in the Reviews space and in spaces that aren't a story's), put in front of its argv as `env`'s arguments by `placed()` in ui.js (`whereEnv()`: the id and the key checked first, a key that isn't one left out), at the places terminals start, not in the argv builders: `launch()` in stories.js (every story tab: Start work, Resume, Claude, Terminal, Merge and Request approval), `openDesk()`, `startAgent()` in source.js, the tab bar's + elsewhere (`newClaude()`/`newTerminal()` in main.js, the space's story when it's one's) and `startReview()`. The plugin's hook and `get_story` read them (Claude Code plugin, above). `bin/gh` is Kelpie's own gh (#103): it finds the real gh further on `PATH` (absolute folders only, never its own folder nor another Kelpie gh's this run came through, `KELPIE_GH_SKIP`, so two copies on `PATH` don't run each other for ever; none: exit 127), asks `gh auth token --hostname github.com --user <login>` per run (the login checked as `GITHUB_LOGIN`, by a `case` pattern) and execs it with `GH_TOKEN` (that run's environment only), failing rather than acting as someone else; it turns tracing off first (macOS's sh takes xtrace from an exported `SHELLOPTS`, which printed the token) and never passes the token to a command; left as they are: a `GH_TOKEN` already set, no account, `auth login|logout|switch|refresh|setup-git|git-credential` (so git's account never changes), help, version and completion; a `GH_HOST` other than github.com runs as it is (no token), and arguments naming a `ghe.com` or `github.localhost` host are refused, as gh sends `GH_TOKEN` to those too; `gh auth status` and `gh auth token` get the account too, status with a line naming it (#102).

Kelpie can't put its folder first in `PATH` itself: login shells put gh's own folder first again (macOS's `/etc/profile` does, tested), so one line at the end of the person's shell setup does (`GH_SHELL_LINE` in setup.js: `KELPIE_GH_BIN` first only when absolute with no colon, as a relative folder would run what the shell's folder holds; `githubEnv()` sets it only so too; with no account it sets `KELPIE_GH_ACCOUNT=` empty, an assignment as `env` takes options only first, so one inherited from where Herdr started (a profile's terminal) can't stand in for Default; gh.sh unsets it and `githubAccounts()` runs `env -u KELPIE_GH_ACCOUNT gh`), and every program started there inherits it; Herdr starts every agent through the person's `zsh -lic`.

A `gh()` shell function given before reached only gh typed in the shell, never a program running it (a team's CLI, a script). The GitHub page shows the line to copy with Check my shell (`gh-shell-check.sh`: the login checked by a `case` pattern, as grep checks each line alone; their `$SHELL -lic` with both variables set asks `gh api user` in the shell (`shell=`) and from a plain `sh -c` (`program=`), noting a `GH_TOKEN` of the setup's own (`token=1`), 15 s at most (the shell in a process group of its own, `setsid` or `set -m`, killed whole with KILL, as an interactive shell ignores TERM and what it started keeps the output open; `KELPIE_CHECK_FOR` for the tests); logins compared without case, as GitHub's are; `shellVerdict()` turns that into what to do).

Claude runs commands through a snapshot of the shell setup (`<config>/shell-snapshots/`); a resumed session was seen taking none and running on one older than the setup, so the guides say a new agent picks it up, and to keep the main account gh's active one; the README's "Several accounts" guides both accounts and shows the same lines (a test keeps them equal). The Kelpie footer (main.js `workClaude()`) shows the active profile's account only, never what has focus: its newest cached 5h and week limits (`~/.cache/kelpie/limits/`, newest file per `config` with limits) in fixed-width columns, "reset" once a window's reset time passed, the model and age in the tip. Each column's tip says when its window resets (`resetTip()`: "Resets in 1h 20m, at 3:40 PM", past a day "Resets Sat 5:00 PM"); at 85% and up (`LOAD.limit`'s red) the reset time also follows the share, short (`resetShort()`: "20m", "1h20", "16h", "Sat"), and that column may grow past its width, the account name truncating first. `side-foot` is 70px for that line

## Claude's limits

Claude limits come from Claude Code's status line: each Claude config's `settings.json` set to run `mods/kelpie/claude-statusline.sh` (the user's own setup, see README), which saves each session's data (with `config`, its `CLAUDE_CONFIG_DIR`, null when unset) to `~/.cache/kelpie/limits/`, kept 7 days, and prints nothing

## Account boundary

Account boundary (`boundary.js`, #254): profiles may run on different Claude accounts (`claude.config`) so that one account's work stays away from the other's, so the plugin's tools hand a Claude only its own profile's work, never another's and never every profile's; Kelpie's own views still read everything. Who asks is `whoAsks(req)`: the asking agent's terminal first (an agent Herdr lists, in a profile's space: that profile, whatever `KELPIE_PROFILE` says), else What next?'s `profile`; its account is the terminal's own Claude session's (`claudeSession()`), else what the server says (`origin()`'s `account`, from `CLAUDE_CONFIG_DIR`, `""` for Claude's own `~/.claude`, `accountKey()`), unknown (an older plugin) counting as none; a profile found counts only on its own account (`accountOf()`), so a personal-account Claude in a work space gets nothing, not even the personal profiles. `allowedFor()`: its own profile; one in no profile's space, the profiles on its account; `mayReachAgent()`: an agent in no profile's space only for an asker on that agent's own session's account. `profileFor()` is the one profile a request is about (Next's tools, `get_story`, `show_passage`): the asker's own, else the only one on its account, never the one shown (`requestProfile()` goes through it); `show_passage` also needs that profile shown, and says to switch to it.

Two profiles the person paired (the profile dialog's Agents page, Other profiles: a switch per other profile, saying whether it's on another Claude account) reach each other's agents, both ways, and nothing else (`agentProfilesFor()`, `mayReachAgent()`; settings, Next and stories stay each profile's own): shared `kelpie.share`, `["<id>|<id>"]` with the ids sorted, one entry for both sides, written only by the dialog's Save (`setShare()`/`sharedWith()` in config.js, `saveShares()` in setup.js), never by an agent's request (no section takes it) or a command; a deleted profile's pairs go with it (`saveProfile()`). Such an agent comes marked `crossed` (its profile's name, `crossedTo()`), and find_agents' answer tells the Claude to say so whenever it uses or messages one.

Refusals never name the profile kept back. The hook's line from saved stories needs the profile's account too (`where_from_shared()` in server.py). A request file can be written by any program, so this keeps a misled Claude from being handed another account's work, not one set on crossing (security.md). Tests: `tests/js/boundary.test.mjs`, and the boundary cases in `find-agents`, `profile-apply`, `next-plugin`, `where` and `passage` tests, `test_plugin.py`

## Sessions

Sessions: `sessions.py` indexes `~/.claude*/projects/<folder, encoded>*/*.jsonl` (titles, last prompt), caching per file path what it read and the byte offset it read to, with mtime/size/inode, in `~/.cache/kelpie/` (private, as it holds prompts and titles: the folder 0700, the file a fresh 0600 `mkstemp` put in place by `os.replace`, so a link there is replaced, never written through; one index shared by every folder and limit: each run merges into it, dropping deleted files). An unchanged file isn't read; one that grew (a live session) is read on from its offset (whole lines only), a replaced or shorter one from the start. Each session also says its `config` folder when not the default `~/.claude`, so resuming it runs on that account.

A profile's earlier sessions are its own Claude account's only (`claude.config`, else `~/.claude`; sessions.py's third argument reads only that folder), the plain sidebar's "Earlier sessions" (sessions.js) and the story list's read alike (`fetchSessions()` in stories.js: Resume ▾, More, the Desk's earlier sessions, find_agents' `resumable`; #157), so profiles on different accounts never mix, wherever a session started. Two profiles on one account sharing a folder still see each other's: a session records its folder and account, not a profile. It runs on the space's machine (passed with `python3 -c`)
